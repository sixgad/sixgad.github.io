给小白的 Hermes API Server 图解
——把你的 AI 管家变成外卖店

只讲人话,6 分钟看懂:远程调用 · 并发 · 那些看不懂的日志

一、Hermes 本来长什么样?

Hermes Agent 是一个很能干的 AI 管家:它会聊天、跑命令、读写文件、搜网页。但它平时只跟你一个人说话——你在电脑上打开它,像用微信一样打字。

你 💬 ➜ Hermes

一个人对一个人,别人插不进来。

问题是:程序不会打字。你的 Python 脚本、公司的系统、别人的电脑,想找 Hermes 帮忙时,没法「打开窗口聊天」。

解决办法:给 Hermes 开一家「外卖店」——API Server。程序们像点外卖一样下单,Hermes 在后厨做好,打包返回。

二、开店三步

开店只要三条命令(在跑 Hermes 的那台机器上):

hermes config set API_SERVER_ENABLED true   # ① 开店
hermes config set API_SERVER_KEY 我的暗号    # ② 定暗号
hermes gateway                               # ③ 开门营业

点单(任何机器上):

from openai import OpenAI

client = OpenAI(
    base_url="http://服务器IP:8642/v1",   # 店门口,别忘 /v1
    api_key="我的暗号",                    # 对上暗号才卖
)

# 完整点单写法:model 就是菜单上的菜名
resp = client.chat.completions.create(
    model="hermes-agent",                # 明确点"管家默认"这道菜
    messages=[{"role": "user", "content": "帮我列出当前目录下的文件"}],
)
print(resp.choices[0].message.content)

点完单在门口等(Hermes 会真的去干活,可能要几分钟),菜好了端回来。想看菜单上有什么菜:

models = client.models.list()            # GET /v1/models
for m in models.data:
    print(m.id)                          # → "hermes-agent"(加菜后还会更多)
两个最容易踩的坑:
① 默认只绑 127.0.0.1(只有本机能点),要让别人点得改成 API_SERVER_HOST=0.0.0.0;
② 地址必须带 /v1 尾巴,少了它「连接测试通过但就是没模型」。

三、外卖店的「后厨规则」:并发 = 灶台数

这家店默认只有 10 个灶台(一次最多同时炒 10 单)。第 11 个单子进来,店员直接说:「人太多了,稍后再来」——这就是日志里的 429 Too many concurrent runs。

想多炒几单?改配置加灶台:

gateway:
  api_server:
    max_concurrent_runs: 100   # 灶台从 10 加到 100;写 0 = 不限
但灶台不是越多越好:每一单背后都是 Hermes 动真格地干活(调 AI、跑工具),真正的天花板是上游 AI 模型的吞吐和那台服务器的 CPU/内存。实测:100 并发下全部成功、零拒绝,但每单平均 18 秒——因为每道「菜」都在深度思考(reasoning_effort: xhigh)。想让店更快,先把思考档位调低,比加灶台管用得多。

四、那条吓人的日志:BLOCKED 不是出错

日志里刷屏的这段,读起来像出了大事:

WARNING ... BLOCKED: execute_code runs arbitrary local Python
(including subprocess calls that bypass shell-string approval
checks). This session runs on an unattended platform (api_...

翻译成人话:

Hermes 想用「亲手写代码精确计算」这个本领(execute_code),但保安拦住了:

保安的理由:外卖单子来的渠道(API server)是「无人值守」的——出了事没有人能当场按「同意」。一个能跑任意代码的本领,没人盯着就放行,太危险。所以:宁可拦下,让它换个笨办法。

放行的开关(想清楚再开!):

approvals:
  unattended_mode: approve   # 默认 deny;⚠️ 必须写在 YAML 顶层
血泪教训:这个块要写在配置文件的顶层。第一次写的时候缩进多了一层,变成 display.approvals——Hermes 根本不看那里,等于白写。YAML 的缩进 = 归属,差一格就是另一个抽屉。改完任何配置都要重启 gateway 才生效。
安全提醒:放行之后,任何拿到暗号(API key)的人,都能在这台服务器上跑任意代码。所以:暗号要够长、要常换、端口只对可信网络开门。

五、菜单上为什么只有一个菜?

刚开店时查菜单(GET /v1/models),只看到一个菜:

["hermes-agent"]   ← 就这一个?

这也是故意的。这家外卖店卖的其实是「让 Hermes 干活」这一个服务,菜名 hermes-agent 的意思是「管家默认配置,看着办」。后厨用什么 AI 模型,是店长(你)在 model: 里定的,客人不用管。

想让菜单丰富点?加「别名菜」——每个名字对应后厨的一种做法:

platforms:
  api_server:
    extra:
      model_routes:
        qwen:                    # 客人点 "qwen" →
          model: "qwen3.8-flash-next"
        glm:                     # 客人点 "glm" →
          model: "glm-4.7"
          provider: "zai"

重启后菜单变成:["hermes-agent", "qwen", "glm"]。客人点单时把菜名换掉即可:

resp = client.chat.completions.create(
    model="qwen",                            # ← 点"qwen"这道别名菜
    messages=[{"role": "user", "content": "查一下今天的新闻并总结"}],
)

你看到的真相怎么办
429 Too many concurrent runs灶台满了(默认 10),礼貌拒单调大 max_concurrent_runs,重启
BLOCKED: execute_code …保安拦下危险本领(无人值守渠道没人审批),不是故障无害可忽略;确需放行 → 顶层 approvals.unattended_mode: approve
菜单只有 hermes-agent设计如此,一个名字代表「默认整套服务」想加菜用 model_routes 别名
改了配置没效果没重启,或缩进错了位置检查缩进 → hermes gateway stop && hermes gateway
并发通了但慢瓶颈在单单耗时(深度思考)不在灶台数调低 reasoning_effort,优先于加并发
连不上 / 连上没模型默认只绑本机 / 地址少了 /v1API_SERVER_HOST=0.0.0.0 / 补上尾巴

核心心法一句话:

API Server = 外卖店 · 并发 = 灶台 · 429 = 拒单 · BLOCKED = 保安 · 配置 = 菜单
改配置三件套:写对缩进、放对层级、重启生效
